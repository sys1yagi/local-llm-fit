# local-llm-fit

**LLMが実際の業務にどこまで耐えるかを、自分の環境で測るツールです。**

同じ業務タスクを何本も同時に投げて、「答えが合っているか」と「どれだけ待たされるか」を
一緒に記録します。出てくるのは、**同時に何本まで基準内でさばけるか**の表です。

手元のPCでも、社内サーバでも、オンプレのGPU機でも、OpenAI互換のAPIが出ていれば測れます。
外部のAPIに向けることもできますが、その場合に見えるのは自分の機材の限界ではなく
提供元の混み具合なので、読み方が変わります。

## 何が分かるか

速さと正しさは、片方だけでは判断材料になりません。
1人で使うぶんには十分速いのに、数人が同時に使った瞬間に待ち時間が跳ね上がる、
ということが普通に起きます。逆に、待ち時間が短くても答えが業務の水準に届かなければ意味がありません。

速度を測るツールは返ってきた答えの中身を見ず、答えの質を測るツールは同時利用を再現しません。
このツールは両方を同時に記録して、**あらかじめ決めた基準に照らして
「同時に何本までなら仕事になるか」**を1つの表で返します。

## 出力の例

- **やらせた仕事**: 日本語の請求書から、決められた項目のJSONを抜き出す（48件・seed 501）
- **測った環境**: Apple M5 Max / メモリ128GB のノートPC
- **モデル**: `ornith-1.5-35b-a3b` を LM Studio で実行

| 同時に投げた本数 | 最初の文字が出るまで | 返り終わるまで | 1秒あたりの生成量 | 正答率（95%区間） | 判定 |
|---:|---:|---:|---:|---:|:--|
| 1 | 0.27秒 | 4.37秒 | 77 トークン | 46/48 96% (86〜99%) | 基準を満たす |
| 2 | 0.74秒 | 14.11秒 | 47 トークン | 45/48 94% (83〜98%) | 正答率が足りない ※ |
| 4 | 2.24秒 | 22.23秒 | 58 トークン | 45/48 94% (83〜98%) | 正答率・応答とも足りない ※ |
| 8 | 21.05秒 | 40.03秒 | 62 トークン | 45/48 94% (83〜98%) | 正答率・応答とも足りない ※ |
| 16 | 55.02秒 | 71.12秒 | 61 トークン | 45/48 94% (83〜98%) | 正答率・応答とも足りない ※ |
| 32 | 119.67秒 | 135.73秒 | 61 トークン | 47/48 98% (89〜100%) | 応答が遅い |

※ 正答率の95%区間の上端が基準を超えている行。基準を割ったと断定するには件数が足りない。

> **この環境とこのモデルなら、同時1本まで。**

### 表の読み方

- **同時に投げた本数**: 何本を同時に処理させたか。登録ユーザー数ではありません。
  人は読んだり考えたりしている時間の方が長いので、同時にさばける本数の
  10〜20倍の人数が使えるのが目安です
- **最初の文字が出るまで / 返り終わるまで**: 利用者が実際に待つ時間。
  48件のうち遅い方から3件目の値（p95）
- **1秒あたりの生成量**: その本数のとき、環境全体が1秒間に作れた文字量
- **正答率**: 48件のうち、抜き出したJSONが正解と一致した件数。
  どの行も同じ48件の正解を使い、文面だけ行ごとに変えているので、行をまたいで比べられます。
  括弧内は95%区間（Wilsonスコア区間）で、件数が少ないほど広がります
- **判定**: 割った基準をそのまま書きます。`※` が付く行は、点推定では正答率が
  基準を割っているものの、区間の上端が基準を超えていて断定できない行です

基準は [`tasks/invoice-json-ja.yaml`](tasks/invoice-json-ja.yaml) に書いてあり、
この例では正答率95%以上・最初の文字まで2秒以内・返り終わるまで15秒以内・エラー0 です。

### この例から読めること

**本数を増やしても、こなせる仕事量は増えません。**
1秒あたりの生成量が最も大きいのは同時1本のとき（77トークン）で、
本数を増やすと 47〜62 トークンに下がります。
一方で1件が返り終わるまでの時間は 4.37秒 → 135.73秒と31倍。
**同時に投げた本数のぶんだけ待たされるだけで、処理の総量は増えません。**
毎秒何トークン出るかだけを見ていると、この頭打ちは見えません。

**待ち時間が崩れる境目は2本と4本の間です。**
最初の文字が出るまでは2本で0.74秒ですが、4本で2.24秒になり、
基準の2秒を割ります。8本では21.05秒。
推論が遅くなったのではなく、順番待ちが始まったということです。
何本まで置けるかを決めているのはこの境目で、モデルの生成速度ではありません。

**正答率は94〜98%で、同時本数と関係なく動きます。**
どの行も同じ48件の正解を（文面だけ変えて）測っているので、行をまたいで比べられます。
基準の95%を割っている行はいずれも区間の上端が98%なので、
**基準を割ったと断定するには48件では足りません**（表の `※`）。

区間を見る意味は、件数が少ないときにはっきり出ます。
同じツールで測った業務日報のタスクは12件なので、
**全問正解（12/12）でも区間は76〜100%**です。
100%と出ていても「95%以上ある」とは言えません。

落ちるのは品名の取り違えで、「A4コピー用紙（500枚）」を「（50枚）」と読んだり、
「Webサイト運用費」を「ウェブサイト運用費」と書いたりする例です。
まれに出力そのものが壊れ、同じ行を繰り返してJSONが閉じないまま終わることもあります。

**片方だけでは、この答えは出ません。**
速度だけ見れば「毎秒99トークン出ている」で終わり、
正しさだけ見れば「96%取れている」で終わります。
並べて初めて「2本まで」という答えになります。

## 入っている仕事

| タスク名 | 内容 | 入力の長さ | 主に効いてくるもの |
|:--|:--|--:|:--|
| `invoice-json-ja` | 請求書から項目をJSONで抜き出す | 約500字 | 答えを書く速さ |
| `long-report-ja` | 2万字の業務日報から、散らばった6件の決定を抜き出す | 約20,000字 | 入力を読む速さ |

長さが違うと待ち時間の内訳が変わります。Apple M5 Max + `ornith-1.5-35b-a3b` で
同時1本を測ると、最初の文字が出るまでは請求書が0.27秒、業務日報が13.6秒でした。
後者は返り終わるまで21.1秒のうち14秒が読み込みで、その間まだ1文字も書いていません。
4本同時にすると最初の文字まで46.4秒かかります（請求書は2.24秒）。
業務日報は1件が重いので12件で回しています。そのぶん正答率の区間は広く、
12/12 でも 76〜100% です。

`--task long-report-ja` で切り替えます。`generator.doc_chars` を変えれば入力の長さも変えられます。

## 使う

必要なものは [uv](https://docs.astral.sh/uv/) と、OpenAI互換のAPIを出す推論環境です。
LM Studio、Ollama、vLLM、SGLang、llama.cpp server、TGI などが該当します。
動いている場所は手元でも社内サーバでも構いません。

```bash
git clone https://github.com/sys1yagi/local-llm-fit
cd local-llm-fit
uv sync

# どんな請求書を渡して、何を正解とするのかを1件だけ見る（LLMは動きません）
uv run fit --dry-run

# 測る
uv run fit --model <モデルID> --concurrency 1,2,4,8,16,32
```

接続先の初期値は `http://localhost:1234/v1`（LM Studio）です。
Ollama なら `--base-url http://localhost:11434/v1`、別のマシンなら
`--base-url http://<ホスト>:8000/v1` のように指定します。
モデルIDが分からないときは `curl <接続先>/models` で確認できます。

行ごとに文面を描き直して投げるので、上の設定では 48件 × 6行 = 288回の呼び出しになります。
Apple M5 Max で15分ほどかかりました。短く試すなら `--samples 12 --concurrency 1,4` です。
`long-report-ja` は1件あたりの読み込みが長いので、同じ件数でも数倍かかります。

結果は `results/` に要約のJSON、`runs/` に全部の応答が残ります（`runs/` はGitに入りません）。

## 結果を見る

測定が終わると、`results/` のJSONの隣に同じ名前のHTMLが出ます。
表と4枚のグラフが入った1枚もので、外部のCSSもフォントも参照しないので、
ネットに繋がっていない状態でもそのまま開けます。

```bash
# 既存のJSONから作り直す（複数まとめて指定できる）
uv run fit report results/<ファイル名>.json

# results/ の全件から、一覧付きのサイトを site/ に作る
uv run fit pages site
```

グラフは4枚です。最初の文字が出るまで・返り終わるまで・1秒あたりの生成量・正答率で、
どれも横軸は同時に投げた本数（対数）。基準は赤い破線で引いてあるので、
実測がどこで線を割るかが見えます。正答率のグラフには95%区間を縦棒で描いていて、
この棒が基準の線をまたいでいる点が、表の `※` と同じものです。

`runs/` に生データが残っていれば、落ちた件の理由と外れた値の内訳も付きます。
残っていなければその節を飛ばして生成します。

**持ち寄った結果の一覧**は main への push で作り直され、
`https://sys1yagi.github.io/local-llm-fit/` に出ます（Pagesを有効にしたあと）。
中身は `uv run fit pages` と同じもので、生データの節だけ落としてあります。

HTMLは生成物なのでGitには入れていません。手元で作り直してください。

## 自分の業務に合わせる

**基準を変える。** `tasks/invoice-json-ja.yaml` の `slo` を書き換えます。
どこまでの間違いを許せるか、何秒まで待てるかは業務ごとに違うので、
同梱の数字（正答率95%・最初の文字まで2秒・返り終わるまで15秒）は仮置きです。

**表記の扱いを変える。** `grading.collapse_whitespace` を外すと、空白の有無も
不正解として数えます。同梱の2タスクは、測りたいのが抜き出せているかどうかなので
立てていますが、帳票の文字列をそのまま転記する必要がある業務では外してください。

**仕事の内容を変える。** `tasks/` にYAMLを1枚と、`src/local_llm_fit/generators/` に
入力を作るPythonを1本追加します。生成する側は「先に正解を作って、そこから文面を組み立てる」
書き方にしてください。そうすれば本文と正解が必ず一致し、seedを固定すれば
誰の手元でも同じ入力になります。

**タスクのversion。** `tasks/*.yaml` の `version` は、そのタスクの定義が何代目かを表します。
**生成器・採点・指示文のどれかを変えたら1つ上げてください。** 測ったときの version は
結果のJSONに残るので、あとから「同じ仕事を測ったもの同士か」を見分けられます。
基準（`slo`）だけを自分の業務に合わせて変えるときは上げなくて構いません。
判定は変わりますが、投げた仕事も採点も同じままだからです。

**実データは使いません。** 入力はその場で合成するので、
リポジトリにも `tasks/` にも実在の書類は含まれていません。
社外に出せないデータを扱わずに済み、評価用のデータが将来モデルの学習に
取り込まれても、seedを変えれば作り直せます。

## 結果を持ち寄る

`results/` に出たJSONをそのままプルリクエストで送ってもらえると、
機材・モデル・量子化の組み合わせごとの実測が溜まり、
[一覧ページ](https://sys1yagi.github.io/local-llm-fit/)に並びます。
1つの環境で測れることには限りがありますが、集まれば
「この構成なら何本までさばける」という比較表になります。

推論サーバの種別は自動では分からないので、`--server-label "LM Studio 0.3"`
のように書き添えてもらえると一覧の列に出ます。省いても測定はできます。

同じ理由で、結果を見比べるのに要るのに自動では取れない項目を、任意の引数で受け取ります。
どれも省けます。省いた項目は `unknown` として記録され、測定は止まりません。

```bash
uv run fit --model <モデルID> \
  --server-label "LM Studio 0.3" \
  --quantization Q4_K_M \
  --server-concurrency 4
```

`--quantization` は量子化の表記、`--server-concurrency` は推論サーバ側に設定した
同時処理数です。後者は待ち時間の変わり方をほぼ決めてしまうのに、APIからは読めません。
量子化を返すサーバなら `--quantization` は省いても自動で入ります。
電源につないでいるかどうかは macOS では自動で記録します。

送る前に、手元で形と数字を点検できます。

```bash
uv run fit check results/*.json
```

見るのは、必要なキーが揃っているか・タスクの version がいまの定義と同じか・
数字の辻褄が合うか（正答数が件数を超えていないか等）の3つです。
プルリクエストでも同じものが動きますが、**警告を出すだけで落としません。**
測り直しを強いるより、事情を書き添えてもらう方が早いためです。

## 測っていないこと

- 負荷のかけ方は「同時にN本を保ち、1本終わったら次を投げる」だけです。
  実際の利用者は前の応答を待たずに次を送るので、問い合わせが一気に集中する業務では
  この測り方は待ち時間を実際より短く見積もります
- 1つのモデル・1つの環境での結果です。モデルの優劣を比べる表ではありません
- 消費電力とメモリ使用量は取っていません
- 行ごとに文面を描き直すため、**行間の正答率には表記の書き分けによるぶれが残ります。**
  正解と難易度の構成は行間で揃えていますが、表層の違いによる差はゼロにはなりません
- 採点の前に落としているのは空白だけです。カナと漢字、大文字と小文字、
  全角と半角の違いは不正解のままです（必要なタスクが出てきたら足します）

測定条件の詳細と、揃えていない条件の一覧は [METHOD.md](METHOD.md) にあります。

## 他のツールとの違い

- 速度と待ち時間を細かく測るなら [GuideLLM](https://github.com/vllm-project/guidellm) や
  [llm-optimizer](https://github.com/bentoml/llm-optimizer) の方が作りが厚いです。
  ただし返ってきた答えが合っているかは見ません
- 答えの質だけなら [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)、
  日本語なら [llm-jp-eval](https://github.com/llm-jp/llm-jp-eval) や
  [Nejumiリーダーボード](https://nejumi.ai) があります。
  ただし複数人が同時に使う状況は再現しません
- 両方を1つでやる先行研究に [Bench360](https://github.com/slinusc/bench360) があります。
  こちらはNVIDIAのGPU専用で、Apple Silicon や llama.cpp では動きません

## English

Docs are in Japanese, because the tasks are Japanese business documents.

It sends a business task at increasing concurrency against any OpenAI-compatible
endpoint, records both answer correctness and latency, and reports the largest
concurrency that still meets the bar you set in `tasks/*.yaml`.
Inputs are synthesised from a fixed seed, so no real data is needed. Each
concurrency level re-renders the *same* ground truth into different wording, so
server-side prompt caching cannot make later rows look faster, while accuracy
stays comparable across rows.

```bash
uv sync
uv run fit --model <model-id> --base-url http://localhost:1234/v1 --concurrency 1,2,4,8
```
